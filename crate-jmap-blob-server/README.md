# jmap-blob-server

JMAP Blob Management method handlers for the `jmap-server` dispatcher:
`Blob/get`, `Blob/set`, `Blob/lookup` and `Blob/convert`
([draft-ietf-jmap-blobext-03]), and `Blob/upload` ([RFC 9404]).

**Status: surface fixed, handlers pending.** `BlobBackend`,
`register_blob_handlers`, `BlobMode` and the `memory` backend are in
place; the four handlers answer `serverFail` until their beads land (see
`PLAN.md`).

## What it is

Backend-agnostic handlers over a `BlobBackend` trait, plus an in-memory
reference backend behind the `memory` feature (`test-helpers` adds test
knobs).

## What it's for

A JMAP server that stores blobs plugs its storage into `BlobBackend` and
calls `register_blob_handlers` on its `Dispatcher`. The crates own wire
validation, method semantics and error mapping; blob storage, the reverse
lookup index and media conversion are backend hooks.

## How to use

```rust,ignore
use std::sync::Arc;
use jmap_blob_server::register_blob_handlers;
use jmap_server::Dispatcher;

// `backend` implements `BlobBackend`.
let mut dispatcher = Dispatcher::new();
register_blob_handlers(&mut dispatcher, Arc::new(backend));
```

Advertise `urn:ietf:params:jmap:blob2` yourself: `{}` in the Session
`capabilities`, and `BlobBackend::blob_capability` in each account's
`accountCapabilities`.

## How it works

- One module per method (`get`, `set`, `lookup`, `convert`), each a public
  `handle_blob_*` function taking the request's creation ids and `using`.
- `BlobBackend: JmapBackend` hooks are RPITIT `+ Send` futures taking the
  caller and account. Hooks with a correct default have one
  (`stored_digest`, `digester`, `blob_chunks`, `image_data`,
  `lookup_type_capability` from `jmap_types::data_types`); the rest have
  none, since any default would put wrong data on the wire.
- `BlobMode::from_using` picks blob2, RFC 9404, or the forbidden mix of
  both (`invalidArguments`).
- `memory::MemoryBackend` (feature `memory`) is the reference backend:
  per-account blobs with ids `B1`, `B2`, ...; inline-only blobs stored as
  bytes and blobs built from other blobs stored as chunk lists of leaf
  blobs; `expires` one hour ahead (five minutes for `noPersist`, `null`
  while referenced); touches honoured up to seven days; a stored sha-256 of
  each whole blob. It builds and lists `application/x-tar` itself (a
  hand-rolled ustar; archives are generated on first read) and runs other
  recipes through a test stub. Feature `test-helpers` adds
  `advertise_for_test`, `add_reference_for_test`, `hide_object_for_test`,
  `set_clock_for_test`, `omit_no_persist_for_test`,
  `stub_converter_for_test` and `fail_deferred_for_test`.

## Gotchas

- Return `Err` from a hook only for a transient failure: it becomes
  `serverFail`. A blob the caller may not see is `Ok(None)` or a
  `notFound` SetError.
- A deferred `Blob/convert` result must be generated by `blob_info` and
  `read_blob_range`; if generation fails, the blob does not exist.

- A request that lists both `urn:ietf:params:jmap:blob` and
  `urn:ietf:params:jmap:blob2` in `using` gets `invalidArguments` from every
  `Blob/*` method (blobext-03 §2.1).
