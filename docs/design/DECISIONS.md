# Design decisions (Mark, 2026-11-13)

1. conditional hook placement: (c) required `begin_set` hook on a separate `ConditionalBackend` trait, wired through an OPT-IN registration path; existing `register_*_handlers` signatures unchanged (non-breaking); the conditional capability is advertised only when a deployment opts in; in-repo reference servers and testjig opt in. Same pattern as object-history's `register_<x>_handlers_with_history`.
2. conditional args without the URI in `using`: reject the whole method with `invalidArguments` when `atomic` is true or `ifUnchangedBy` is non-empty (atomic:false / `{}` / null accepted). Also applies on deployments that have not opted in to conditional (one dispatcher check). Precedent: mail-server rejects metadata writes/filters without the metadata URI (helpers.rs:188).
3. emailpush placement: `emailpush` feature of jmap-mail-types / jmap-mail-server / jmap-mail-client (mdn/sieve precedent); EmailPushBackend does not extend MailBackend so IMAP-only deployments can implement it alone.
4. blob crate names: jmap-blob-types / jmap-blob-server / jmap-blob-client (free on crates.io); Mark's claimed placeholder `jmap-blob` (0.0.1, "RFC 9404") becomes the umbrella re-export crate like jmap-mail, description updated to blobext. Fold epic JMAP-m4nc (RFC 9404 jmap-blob) into JMAP-tna1: blobext-03 obsoletes RFC 9404.
5. object-history scope: (b) the 11 Table 1 "Yes" types AND Task/TaskList AND Mark's private types (chat, graph, scene, vtc) in the first round. Per-type list to settle when filing beads; proposed exclusions: log/ephemeral/notification types (GraphNodeOp, PresenceStatus, ReadPosition, SceneAvatar, VTCParticipant, TaskNotification, by analogy with CalendarEventNotification/EmailDelivery "No"). Follow-ups: ask the Tasks authors to register "Supports History: Yes"; add a "Supports History" line to each of Mark's drafts in ~/PROJECT/jmap-chat-spec.
6. spec-gap stopgaps (implement now, raise upstream): (a) restores count toward maxObjectsInSet; (b) conditional `atomic` covers restores and atomicFailure carries `notRestored` (raise on both drafts); (c) onlyDestroyed queries encode the query kind in queryState so queryChanges routes by it; (d) an object whose final version was discarded is gone (notFound for get/query/restore); memory backend discards oldest first. Offer Mark drafted list message / issues.
7. conditional error codes: (b) `&str` consts `ATOMIC_FAILURE` / `CANNOT_APPLY_ATOMICALLY` in jmap-types' conditional module, built via the custom-error constructor; NOT new MethodErrorType variants (its documented rule: RFC 8620 codes only, extensions are `Other`; precedent OPS_COMPACTED, QUERY_TOO_COMPLEX, CONTENT_POLICY). Non-breaking. Overrides the conditional note's OQ4.
8. conditional client surface: (a) generic `SetCall` in jmap-base-client (any type; conditional + object-history `restore` options) plus `filenode_set_conditional`; non-breaking. Follow-up bead for the next breaking release: give all 30 typed `*_set` fns one growable (non_exhaustive) options parameter carrying conditional and object-history options together.
9. emailpush config normalization: (a) store EmailPushConfig with defaults filled (filter null, properties [], urgency "normal"), return from /get, echo in created/updated (RFC 8620 §5.3). Add to upstream list: emailpush `filter` has no stated default.
10. objectHistory in EmailPushConfig.properties: (c) accept it, then drop it from the stored list during normalization (echoed per decision 9), so pushes stay a true prefix (emailpush l.95) while matching Email/get, which accepts but never returns it without includeReplaced/includeDestroyed (object-history §3.1). Upstream note: suggest emailpush exclude objectHistory like bodyValues.
11. RFC 9404 legacy `urn:ietf:params:jmap:blob`: SERVE it (overrides note Q3). RFC 9404 is the published standard; blobext obsoletes it only "if approved". Bead in JMAP-tna1 ordered right after the blob2 server: Blob/upload + 9404 Blob/get / Blob/lookup behaviour selected by `using` (both in one request is forbidden by -03 §2.1). Blobext note's own gap list (a)-(h), lines 72-80, to be reviewed as a group at the end.
12. chat-client blob methods: fix to -03 now (tna1.1, breaking, CHANGELOG); once jmap-blob-client exists, make them thin #[deprecated] wrappers over it (repo stability policy); remove in the next breaking release.
13. memory backend conversion: (a) hand-rolled ustar archive/extract only, no new deps; every other recipe advertised null; handler logic for all recipes tested via a test-helpers stub converter.
14. data-type registry: one shared table in jmap-types (type name, capability, can reference blobs, can use for state change, supports history), read by blobext and object-history; includes the IETF rows plus Mark's drafts' rows, each citing its draft (Yes for blobs: Chat, Message, Space, CustomEmoji, SceneAsset, SceneObject, SceneAvatar, VTCRecording, GraphNode). Overrides blobext note Q7(b).
15. blobext note's eight gap rulings (a)-(h) (note lines 72-80): all accepted as written; add all eight to the upstream list for the blobext author.

Upstream list (to raise with draft authors; drafts in docs/upstream/2026-11-13/, not yet filed): object-history (a) restores vs maxObjectsInSet, (c) onlyDestroyed queryChanges routing (see 25), (d) discarded final version (see 24); both drafts (b) atomic covers restores + notRestored in atomicFailure; emailpush: filter has no stated default; suggest excluding objectHistory like bodyValues; blobext: rulings (a)-(h), both blob+blob2 in using (21(i)), conditional on Blob/convert (19(2)); RFC 9404 errata: 21(ii) Blob/lookup example notFound, 21(iii) Blob/upload example state fields. ## Follow-up decisions (Mark, 2026-11-13, after filing)

16. emailpush validation: NO required `check_push_subscription_change` hook on PushSubscriptionBackend (non-breaking). Follow the chatPush precedent: jmap-mail-server exposes `check_email_push_change` (plus normalization) that the deployment's `create_push_subscription`/`update_push_subscription` MUST call (memory backend does; docs say MUST); send-time code skips configs failing the same check. The shared PushSubscription/set handler gains a generic, non-breaking echo of extension keys whose stored value differs from what the client sent. Single `/set` registration, so no last-wins conflict with conditional opt-in.
17. conditional opt-in shape: separate additive attach call `register_<x>_conditional` after `register_<x>_handlers` / `register_<x>_handlers_with_history` (MDN/Sieve/graph-edit precedent); no `_with_conditional` variants. Dispatcher wraps whichever /set is registered; `conditional_ready()` gates advertisement. Blob: no `blob_set_atomic` hook (already dropped in the blobext note; bead text must match).
18. object-history args without the URI: same as decision 2 — one dispatcher check on */get, */query, */set for every deployment: `includeReplaced: true`, `includeDestroyed: true`, `onlyDestroyed: true`, non-null `destroyedAfter`/`destroyedBefore`, or non-empty `restore` without the object-history URI -> invalidArguments; false/null/empty accepted. Small bead after H3 (resolves D2). No name collisions in the crates or Mark's drafts.
19. blob conditional details: (1) an ifUnchangedBy pointer to Blob `type` or `expires` (never returned by Blob/get) -> invalidArguments per conditional §3.1 rule 4 (not `forbidden`; overrides blobext note §12 Q1); `size`, `digest:<alg>`, `{}` and `null` work. (2) Blob/convert: `atomic: true` or non-empty `ifUnchangedBy` -> invalidArguments.
20. emailpush delivery input: keep `DeliveredEmail` wrapping `&jmap_mail_types::Email` (public `Email::new`); document that IMAP-only deployments without ObjectID fill id/blobId/threadId/mailboxIds with any valid placeholder, which validation guarantees are never emitted or matched.
21. RFC 9404 serving rulings: (i) both `blob` and `blob2` in `using` -> invalidArguments on every Blob/* call in that request; (ii) 9404 Blob/lookup follows §4.3 normative text (empty arrays, no `notFound`), possible 9404 erratum; (iii) Blob/upload response = accountId/created/notCreated only (9404 §4.1 text over examples), possible erratum; (iv) Blob/upload with non-empty update/destroy -> invalidArguments; (v) keep B24 (RFC 9404 client bindings) at P3. (ii)/(iii) to the upstream list.
22. private-type history (resolves bead D1 / JMAP-tna1.3.6): (1) exclusions confirmed (GraphNodeOp, PresenceStatus, ReadPosition, SceneAvatar, VTCParticipant, TaskNotification); included: Chat, Message, Space, ChatContact, CustomEmoji, SpaceBan, SpaceInvite; Graph, GraphNode, GraphEdge; SceneAsset, SceneRegion, SceneObject; VTCCall, VTCRecording, VTCLivestream. Message follows chat-00 l.782: no prior/destroyed versions after deletion; versions permanently removed on delete/hard-delete. (2) KeyPackage: No. (3) Space destroy purges the history of the Space and everything in it (chat-00 l.1395 "Hard-deletes all records; no tombstones"); overrides the note's retain recommendation. (4) GraphNode restore allowed: restored at its final snapshot (blobId/snapshotSeq), op log restarts empty, post-snapshot edits unrecoverable and documented.
23. JMAP Tasks (Mark: "the WG was wrong to drop it"): (a) Mark writes an updated Tasks draft himself, folding in his 17 jmapio/jmap items (issues #456,#457,#459,#461,#463,#465,#466,#468,#470,#471; PRs #458,#460,#462,#464,#467,#469,#472), JMAP Data Types registrations with "Supports History" (Task, TaskList Yes; TaskNotification No) and Calendars -34 alignment; (b) the tasks crates implement those items now as the de facto reference. No WG approach for now. Tasks history (decision 5) stands; JMAP-tna1.3.23 is superseded by the draft's own registrations. Replaces the 2026-11-02 jmap-tasks-dormant memory.
24. object-history discarded final version (revises 6(d)): backends MUST NOT discard an object's final version while older versions remain (trait docs); the shared retention helper prunes oldest-first only (memory backend already does). The 6(d) "treat as gone" ruling stays only as a fallback for a backend that breaks this rule. Rationale: §3, §4 and §5.1 key on "any version"/"at least one version", so "gone" contradicts the letter; the only conflict is §5.1 "final version" vs §3.1 "prune in any order". Proposed upstream in the object-history issue.
25. onlyDestroyed queryChanges (revises 6(c)): the queryState records the query kind AND the destroyedAfter/destroyedBefore window; if a Foo/queryChanges request does not match the window in the state, answer cannotCalculateChanges (object-history §4 MAY). Upstream issue proposes adding onlyDestroyed/destroyedAfter/destroyedBefore to Foo/queryChanges.
26. emailpush metadata filter conditions: accepted when the account supports metadata (`metadata_info::<Email>`), without requiring the metadata URI in the saving request's `using` (agent's decision-16 consequence confirmed). metadata-05's no-`using` rules (around l.509) cover Foo/set writes, Foo/get defaults and Foo/changes only, and an EmailPush filter is evaluated at delivery time outside any request. Document the reason in the emailpush rustdoc.
